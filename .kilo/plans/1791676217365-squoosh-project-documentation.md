# Squoosh project documentation plan

## Goal and decisions

Create contributor/model-facing documentation in `docs/` that explains how Squoosh is assembled and points maintainers to the right source files when changing behavior. Exclude end-user product guides. Use a short landing page plus focused guides; cover codec integration through native/WASM artifacts as well as TypeScript/UI wiring.

## Documentation work

1. Add `docs/README.md` as the documentation index and developer entry point: prerequisites and existing `npm install`, `npm run dev`, and `npm run build` commands; links to the architecture, feature-development, and codec guides; a concise source-tree map.
2. Add `docs/architecture.md` to explain startup and runtime flow: static/prerendered page, initial app and lazy editor, decode → shared preprocessing → independent compare-side processing/encoding, generated worker bridge/API, service-worker/PWA caching, and build pipeline. Include a source-path map for UI, worker, shared feature metadata, service worker, static site, and Rollup/build plugins. Clarify that image processing is local and analytics is separate.
3. Add `docs/feature-development.md` with change-oriented lookup tables and practical feature workflows. Identify encoder, decoder, processor, and preprocessor source locations; describe client/shared/worker responsibilities and generated registries. Explain the distinction between automatically discovered features and manually wired behavior (notably decoder dispatch and codec/service-worker asset caching). Link to the existing `src/features/README.md` for its feature folder and encoder interface contract rather than duplicating that contract.
4. Add `docs/native-codecs.md` for the codec-to-app path: native source and checked-in/generated JS/WASM locations under `codecs/`, example C++ and Rust build entry points and Docker wrappers, TypeScript worker initialization/feature detection, metadata/options/UI, and when to update service-worker caching. Distinguish normal web-app build (`npm run build`) from rebuilding codec artifacts; do not invent a universal codec build command where per-codec scripts differ.
5. Add a concise link to `docs/README.md` in the root `README.md` so the new guides are discoverable. Keep existing contribution and feature-contract docs in place.

## Boundaries and risks

- Documentation only; no application behavior, scripts, generated files, dependencies, test infrastructure, or codec artifacts change.
- Treat `src/features-worker/index.ts`, `src/client/lazy-app/worker-bridge/meta.ts`, and `src/client/lazy-app/feature-meta/index.ts` as generated by `lib/feature-plugin.js`; direct edits are not the source of truth.
- Verify every path and command against the repository. Clearly qualify optional/containerized native codec builds and note that native codec build requirements vary by codec.
- Use relative Markdown links for repository files and avoid stale line-number references.

## Validation

- Check all new internal Markdown links and referenced source paths against the repository.
- Run Prettier check on the changed Markdown files using the version/config already in the project.
- Run `npm run build`, the build command used by CI, if dependencies/environment are available; confirm it succeeds and leaves no tracked generated-source changes. No lint, typecheck, or test script is defined in `package.json`.
